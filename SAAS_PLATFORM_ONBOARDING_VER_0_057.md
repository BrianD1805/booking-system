# ZipBook Ver-0.057 — Platform administration and invitation-led business onboarding

Based on Ver-0.056. The original practice remains separate. The user elected to use the existing live infrastructure before real customers are activated. No business has been provisioned, no invitation sent and no deployment performed by this build. The new dashboard manages accounts created through this workflow, not the demo or accounts manually provisioned via the old offline script.

## Deploy prerequisites
- Confirm Ver-0.056 database migration and rollback-only two-business isolation SQL passed on the actual Supabase project. Back up the database. Apply `supabase/zipbook_platform_onboarding_ver_0_057.sql` in the Supabase SQL Editor; it adds a private invitation table and grants no tenant access. It is not a replacement for Ver-0.056.
- Generate a dedicated 256-bit platform access key on your own machine: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Store the result in a password manager and add it in Netlify as `ZIPBOOK_PLATFORM_ADMIN_KEY` (server functions environment, production; never use NEXT_PUBLIC_). Do not paste it into chat, email or Git. Use a separate key from the existing master admin key. The dashboard keeps it only in page memory; refreshing or closing the page requires sign-in again. Key rotation invalidates future requests. This is operator-only key authentication, not a full platform identity/MFA system.
- Existing Resend email environment and verified sender required; no new email key. Disable link tracking for sensitive invitation links if it rewrites/removes fragments. A successful send means Resend accepted it, not necessarily inbox delivery. Invitations are valid for 48 hours, sent by email, single-use; resending invalidates the previous one. No plaintext initial passwords are issued.
- Keep `ZIPBOOK_ENABLE_BUSINESS_ACCOUNTS` unset or `0` while verifying the dashboard. Later, explicitly set to `1` and redeploy to allow approved businesses to resolve. The flag alone does not activate any business; activation also requires owner verification and operator confirmation.
- Test: npm ci, npm run test:heartbeat, npm run test:booking-time, npm run test:scheduling, npm run test:saas, npm run test:tenants, npm run test:onboarding, npm run typecheck, npm run build, netlify dev --no-open. Run the previous isolation SQL again. Commit only after checks pass. Use synthetic data and an email address you control, not SPBIO's real details. Accepting an invitation in local testing uses the canonical live join URL; use the deployed 0.057 release for the full email flow.

## Workflow
1. Open https://zipbook.app/platform (locally http://localhost:8888/platform). Sign in with the dedicated key. Verify existing `/admin`, `/book` continue working. Verify tenant hosts cannot access platform APIs and the legacy master key does not work.
2. Add a business in the popup with name, lowercase subdomain prefix, owner name/email, timezone, currency and country. A single transaction creates a disabled practice, inactive owner with unusable password and hashed invitation. Resend delivers the invitation after commit; if delivery fails the business remains disabled and you can resend. Duplicate slugs rejected.
3. The owner opens the email link to https://zipbook.app/join, chooses a password of 14–128 characters. The link token is moved out of the URL by the client and posted only with the password. A transaction locks and validates the invite, sets a salted scrypt password, activates the owner staff record and marks verification complete. Reuse or expiration fails. Diary remains unavailable.
4. Set up `<slug>.zipbook.app` in the existing Netlify site and DNS; verify HTTPS on that exact hostname. No wildcard or DNS automation is provided. Set `ZIPBOOK_ENABLE_BUSINESS_ACCOUNTS=1` if not already enabled; redeploy. On the platform dashboard, choose Enable diary and confirm domain readiness. Owner can then sign in at `https://<slug>.zipbook.app/admin` with their own email/password. The platform does not perform a network check of DNS/HTTPS: confirmation is manual.
5. Owner configures practice profile, business hours, practitioners, weekly schedules, services and service assignments in Admin > Settings, and adds staff. Dashboard displays counts from the registered business. Test with synthetic records; public bootstrap, availability and guest creation remain blocked while diary setup is in progress.
6. Return to platform, choose Open public bookings after checks. Server requires owner verification, active diary, global flag and at least one active practitioner with a working-hours entry and assigned active service. This is a minimum readiness check, not proof all schedules are valid. Public booking URL will then be open; pilot clients can book as guests only. No embed yet.
7. Suspend access preserves data and revokes staff sessions and closes public access; re-enable requires operator confirmation and public booking release again. Already in-flight requests may finish. No business deletion in this release.

## Limitations / follow-up
No open signup, billing, owner recovery, platform MFA, automatic DNS/SSL provisioning, verified custom domains, independent security review, or secure website embedding yet. Existing manually created pilots are not shown in the dashboard and now require onboarding_completed to be true to accept public bookings. Tenant isolation and live end-to-end checks must be completed before real customers; test on the live project only with synthetic records given user decision. Re-check the use of the privileged database connection for platform-only transactions, and assess operational security, protection of patient data, backups, and access logging before marketing a healthcare production service. Full owner invitation acceptance, role enforcement, and real email delivery must be verified on deployed infrastructure. Do not replace SPBIO's existing booking service before those checks and its approval. The locked original client home layout and practice admin remain visually unchanged; the pilot home shows a closed-booking message while pending.
